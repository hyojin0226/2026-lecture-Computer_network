# Task 2 · 주소와 DHCP 분석

## A · 현재 네트워크

- 인터페이스: `172.16.12.43/24` (마스크 `255.255.255.0`), 사설 주소(RFC 1918).
- 네트워크는 `172.16.12.0/24`, 브로드캐스트는 `172.16.12.255`, 사용 가능한 호스트 범위는 `172.16.12.1–172.16.12.254`다. Task 1의 범위 계산과 일치한다.
- 기본 게이트웨이 `172.16.12.1`은 이 서브넷 안에 있다. 같은 링크의 호스트가 게이트웨이로 프레임을 전달해야 하므로 로컬 서브넷에서 직접 도달 가능해야 한다.
- 외부에서 관측한 주소는 `addresses.json`에 기록했다. 인터페이스 주소와 외부 주소가 다르므로 최소 한 번 NAT가 적용된다. 단말만으로는 NAT 계층 수를 확정할 수 없다. 라우터의 WAN 주소와 외부 관측 주소를 비교하고, WAN이 사설 주소 또는 `100.64.0.0/10`이면 상위 NAT가 추가로 있음을 확인할 수 있다.

## B · 휴대폰 핫스팟

- 인터페이스: `172.20.10.2/28`, 게이트웨이 `172.20.10.1`. 네트워크 `172.20.10.0/28`, 브로드캐스트 `172.20.10.15`, 사용 가능한 범위 `172.20.10.1–172.20.10.14`다.
- 두 연결에서 사설 주소와 서브넷 마스크가 바뀌었고, 외부 관측 주소도 바뀌었다. 각 네트워크의 DHCP 주소 할당 범위와 인터넷 출구 NAT/통신사가 다르기 때문이다. 정확한 두 외부 주소는 `addresses.json`에 있다.
- 핫스팟도 사설 주소를 할당하고 외부 주소와 다르므로 최소 한 번 NAT가 확인된다. 이동통신사 CGNAT 여부는 핫스팟 단말의 주소만으로 단정하지 않았다.

## C · DHCP DORA (공식 trace, 경로 B)

- 직접 캡처 대신 교재 공식 9판 DHCP trace를 사용했다. Discover/Offer/Request/Ack 네 메시지가 모두 있다.
- Discover의 IP 출발지는 `0.0.0.0`, 목적지는 `255.255.255.255`다. 클라이언트는 아직 임대 주소가 없고 DHCP 서버 주소도 모르므로, 출발지 주소를 쓸 수 없으며 브로드캐스트로 서버를 찾아야 한다.
- trace의 Offer/Ack는 서버 `192.168.86.1`에서 제안 주소 `192.168.86.65`로 전달됐다. Ack는 클라이언트가 사용할 주소를 알게 된 뒤라 브로드캐스트가 필요하지 않다.
- 임대 시간은 `86,400초`(24시간), 갱신 시점 T1은 임대 시간의 절반인 `43,200초`(12시간)다.
